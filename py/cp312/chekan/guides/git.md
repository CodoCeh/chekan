## Что это и когда брать

Git (система контроля версий) запоминает каждую версию файлов проекта. С ним любую правку можно посмотреть, сравнить и откатить. Бери git при любой правке кода или текстов в проекте, где уже есть папка `.git`.

Когда НЕ брать: разовые файлы без истории и черновики в песочнице. Не создавай репозиторий в чужой папке без просьбы.

## Установка и проверка

```bash
git --version
```

Если команды нет, на macOS её ставит `xcode-select --install`, на Linux — пакет `git`. Ставить что-либо — только после «да» пользователя.

## Порядок работы

1. Посмотри состояние: `git status --short`. Чужие незакоммиченные правки не трогай.
2. Создай ветку (отдельную линию правок) под задачу: `git switch -c fix/<суть>`.
3. Делай маленькие правки. Одна мысль — один коммит (сохранённый снимок).
4. Перед коммитом прочитай дифф (разницу «было/стало») целиком: `git diff`, затем `git diff --staged`.
5. Добавляй файлы по имени, а не `git add .`, чтобы не захватить лишнее.
6. Коммить с понятным сообщением в стиле репозитория.
7. Перед сдачей сравни ветку с основной: `git diff main...HEAD --stat`.
8. Пуш и слияние — только если об этом просили.

## Готовые команды

```bash
git status --short
git switch -c fix/greeting
git diff
git add app.py
git diff --staged --stat
git commit -m "fix: greeting text"
git log --oneline -5
git log --oneline --graph -5
git diff main...HEAD --stat
git blame -L1,1 app.py
```

Отложить незаконченное и вернуть:

```bash
git stash push -m wip
git stash list
git stash pop
```

Откат. `revert` создаёт новый коммит-отмену и не переписывает историю — безопасен для общих веток. `reset` двигает ветку назад — только для своих неопубликованных коммитов.

```bash
git revert --no-edit HEAD
git restore app.py
git reset --soft HEAD~1
git reflog -3
```

`git restore` выбрасывает незакоммиченные правки файла насовсем. `git reflog` показывает, где была ветка раньше, и спасает после ошибочного `reset`.

Секреты — в `.gitignore` (список файлов, которые git не отслеживает):

```bash
printf '.env\n*.key\n__pycache__/\n' >> .gitignore
git check-ignore -v .env
git rm --cached config.ini
git log --all --oneline -- config.ini
```

`git rm --cached` перестаёт отслеживать файл, но в старых коммитах он остаётся. Утёкший ключ надо отозвать (см. учебник `secrets`).

## Частые ошибки

- `git add .` захватывает `.env`, логи и мусор. Добавляй по именам и смотри `git diff --staged`.
- `git reset --hard` и `git checkout .` стирают чужие незакоммиченные правки. Сначала `git status`, при сомнении — `git stash`.
- `reset` на уже опубликованной ветке ломает историю коллегам. Для общих веток — только `revert`.
- Один огромный коммит «правки» нельзя ни проверить, ни откатить частями.
- Файл добавили в `.gitignore`, но он уже отслеживается — git продолжает его коммитить. Нужен `git rm --cached`.
- Сообщение коммита не говорит, что изменилось. Пиши суть: «fix: пустой ответ при 404».
- Работа прямо в `main` без ветки. Откатить такую серию правок труднее.

## След для Проверяющего

Положи в папку результатов задачи:

- `git-log.txt` — вывод `git log --oneline main..HEAD`.
- `git-diff.patch` — вывод `git diff main...HEAD` (полный дифф ветки).
- `git-status.txt` — вывод `git status --short` после сдачи; он должен быть пустым или с объяснением каждой строки.

В отчёте назови ветку и хеши коммитов.
