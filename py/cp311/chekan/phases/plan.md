## План

Нарезка на таски. Граница между тасками стоит переориентации свежего контекста — десятки тысяч токенов, — поэтому таск обязан окупать свою границу.

### Сколько тасков

Вилку задаёт масштаб: малая — 2–3, средняя — 4–8, крупная — 9–16. Больше шестнадцати — дробите не задачи, а сам прогон.

### Каким должен быть таск

**Вертикальный срез, а не слой:** «схема + запрос + обработчик + тест для одной функции» — таск; «все модели» — слой, он ничего не демонстрирует. Два теста: **окупаемость** (то, что исполнитель узнает в этом куске, дороже границы?) и **соседство** (два таска правят одни файлы — это один таск). Крупный рефакторинг ведите так: новое рядом со старым → вызовы пачками → снос старого.

### Как заводить

```
chekan task add 01 --title "..." --requirements R01 R02 --deps  --zone src/bot/ \
    --verify "python3 -m pytest tests/test_bot.py -q"
```

- **`--requirements`** обязательны: таск без требования не пройдёт гейт.
- **`--deps`** — таски, которые закроются раньше.
- **`--zone`** — каталог, который таск правит; единственное место плана для путей. Два таска в одной зоне без зависимости столкнутся при параллельном запуске — гейт это поймает.
- **`--verify`** — команда-доказательство. Придумайте её сейчас, а не в конце.

### Гейт G3 — прослеживаемость в обе стороны

Каждое живое требование ведёт хотя бы к одному таску, каждый таск — хотя бы к одному требованию; нет циклов в зависимостях и столкновений по зонам. Проверка: `chekan gate G3`. Брать таски в работу можно только после перехода в разработку (`chekan advance`).

Модель: сильная — ошибку плана дешевле предупредить, чем ловить на сборке.
