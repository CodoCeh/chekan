## Что это и когда брать

Автотесты — маленькие программы, которые сами проверяют, что код работает как задумано. Для Python есть pytest (популярная библиотека тестов) и встроенный unittest. Для JavaScript — `npm test` и встроенный в Node модуль `node:test`. Бери тесты после каждой правки кода и всегда при починке бага.

Когда НЕ брать: тексты, таблицы и документы без кода. Там нужна сверка глазами или по чек-листу.

## Установка и проверка

```bash
python3 -c "import unittest" && uv run -q --with pytest python -m pytest --version
```

Если у проекта своё окружение (`.venv`), запускай его pytest: `.venv/bin/pytest -q`. Иначе `uv run --with pytest` берёт pytest временно и без следа. Ставить что-либо в систему — только после «да» пользователя.

## Порядок работы

1. Найди, как проект уже запускает тесты: `pytest.ini`, `pyproject.toml`, раздел `scripts.test` в `package.json`. Используй ту же команду.
2. Прогони все тесты до правки. Запиши, что уже падало, — это не твоя поломка.
3. На баг сначала напиши тест, который его воспроизводит. Убедись, что он падает с той же ошибкой.
4. Исправь код. Тот же тест должен позеленеть.
5. Добавь крайние случаи (граничные значения): пустой список, ноль, отрицательное, `None`, юникод, очень большое.
6. Прогони весь набор. Новые красные тесты — твоя поломка.
7. Сохрани вывод последнего прогона в след.

## Готовые команды

Пример теста с крайними случаями (`test_calc.py`):

```python
import pytest
from calc import avg

def test_avg_empty():
    assert avg([]) == 0

@pytest.mark.parametrize("xs,want", [([1], 1), ([-1, 1], 0), ([0.1, 0.2], 0.15)])
def test_avg_edges(xs, want):
    assert avg(xs) == pytest.approx(want)
```

Запуск:

```bash
uv run -q --with pytest python -m pytest -q
uv run -q --with pytest python -m pytest -q -x "test_calc.py::test_avg_empty"
uv run -q --with pytest python -m pytest -q -k edges
uv run -q --with pytest python -m pytest -q --lf
uv run -q --with pytest --with pytest-cov python -m pytest -q --cov=calc --cov-report=term-missing
uv run -q --with pytest python -m pytest -q --junitxml=report.xml
```

`-x` останавливает прогон на первой ошибке. `-k` выбирает тесты по части имени. `--lf` перезапускает только упавшие в прошлый раз. `--cov` показывает покрытие (какие строки кода тесты не задели) в колонке `Missing`.

unittest без сторонних библиотек:

```bash
python3 -m unittest -v test_calc_ut
python3 -m unittest test_calc_ut.AvgTest.test_empty
```

Node:

```bash
npm test
node --test --test-name-pattern=sum
```

## Частые ошибки

- Тест написан после фикса и ни разу не падал. Он может ничего не проверять. Сначала красный, потом зелёный.
- Сравнение дробных чисел через `==`. `0.1 + 0.2 != 0.3`, нужен `pytest.approx`.
- Запуск системным pytest вместо проектного `.venv`. Версии библиотек другие, результат врёт.
- Тест ходит в сеть или в боевую базу. Он нестабилен и может испортить данные. Подменяй внешнее заглушкой (mock — подставной объект).
- Проверяется только «счастливый путь». Баги живут на краях: пусто, ноль, ошибка ввода.
- Падающий тест помечают `skip`, чтобы стало зелёно. Это прячет баг.
- В отчёте «тесты прошли» без вывода. Проверяющий не может это проверить.

## След для Проверяющего

Положи в папку результатов задачи:

- `tests-before.txt` — вывод прогона до правки.
- `tests-after.txt` — вывод полного прогона после правки, с итоговой строкой вида `5 passed`.
- `report.xml` — отчёт `--junitxml`, если проект его поддерживает.
- Имя нового теста на баг и строку, с которой он падал до фикса.
