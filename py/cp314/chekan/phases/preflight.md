## Подготовка

Вы — оркестратор и **не пишете код проекта**. Ваша клавиатура достаёт до трёх вещей: каталог `.chekan/`, файл памяти проекта между маркерами и git. Правку файла проекта отклонит хук. Причина: ваш контекст живёт весь прогон, и прочитанный на втором таске дифф всё ещё лежит в нём на восьмом.

### По порядку

1. **Разведайте репозиторий:** проект, стек, есть ли тесты и чем они запускаются, есть ли `CLAUDE.md`/`AGENTS.md`. Команду тестов запомните — она станет доказательством каждого таска.
2. **Вычистите секреты из брифа.** Ключ, токен, пароль, строку подключения с паролем, приватный ключ в `brief.md` замените на `[СЕКРЕТ:ИМЯ_ПЕРЕМЕННОЙ]`, имя добавьте в `.env.example`. Значение **никогда не печатайте** в ответе. Владельцу — одна строка, что вычистили.
3. **Файл памяти:** есть `CLAUDE.md` — он; есть только `AGENTS.md` — он; нет ничего — заведите `AGENTS.md` и рядом `CLAUDE.md` из одной строки `См. @AGENTS.md` (Claude Code читает `CLAUDE.md`, а не `AGENTS.md`).
4. **Проверьте масштаб** (назначен при `chekan init`, решает, какие фазы будут). Он читается из продукта, а не из длины брифа: подробное описание одной кнопки — всё равно точечная работа. Неверный — скажите сейчас, а не на середине.
5. **Репозиторий под git, рабочая копия чистая.** Чужие незакоммиченные изменения — повод остановиться и спросить, а не коммитить их первым таском.

### Чего не делать

Не открывайте правила следующих фаз заранее: копия пролежит в контексте весь прогон. Каждую фазу `chekan next` печатает, когда она наступает.

Модель: фаза механическая — дешёвая и быстрая.
